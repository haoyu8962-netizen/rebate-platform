# tools/ops：编排脚本

编排会话（Claude 主会话）用来推进任务的脚本：台账、在途状态与失败熔断、用量账本（只记账）、看板、任务书、交接、沙箱外验证。规则出处是规划仓库 `规划/11_开发协作与自主推进.md`（下称 11），本文件只写用法和现状。

本目录是保护路径第三类（11 §4.4）：改动要负责人确认。脚本一律从可信副本运行（11 §2.4），可信副本建好前就是主检出；从 `couli-runs/worktrees/<编号>` 下运行一律拒绝。

### 轮次怎么计（`state.ts`）

- 五个计数器各有上限：Codex 写规则测试 `test` 3 次；Opus 实现 `impl` 3 次；换家实现 `handover` 1 次（规划/11 §2.5，只限 RV0 / RV1）；规则测试评审 `spec-test` 2 轮；代码评审 `code` 3 轮（`money`、`general`、`contract` 共用；负责人 2026-10-02 由 2 轮提高到 3 轮，`ops/approvals.yaml` 第 17 条）。原来是一个评审计数器共 2 轮；`test`、`handover` 是 2026-10-05 分工切换时加的（`ops/approvals.yaml` 第 19 条，规划评审 RO-07）：Codex 写测试的 `impl` 模式调用不再计入实现次数。只有三个计数器的旧状态文件照常读，`test`、`handover` 当 0。
- Codex 调用记在哪个计数器上，看它 `meta.json` 的 `phase`（`codex-run.sh impl --phase test|handover`）；没有 `phase` 的旧调用（2026-10-05 前的 Codex 实现）记 `impl`。
- `bump-attempt <编号> test|handover`（`dispatch.sh` 按阶段调）、`bump-attempt <编号> impl`（编排者起 Opus 实现子代理前调）或 `bump-attempt <编号> review --review-type <类型>`（编排者在评审前调）在**派发前**计数并落盘，同时记一条待结算（`pending_bumps`：`kind`、`engine`、`bumped_at`）；用完了退出码 1、不写文件。
- `settle <编号> --meta <meta.json>`（`codex-run.sh` 每次调用结束后调）：先把这次调用与一条同 `kind` / `engine`、`bumped_at` 在调用开始前不久的未消耗待结算配对（CT-06zxk，FU-OPS-COUNTER）；**配不到即这次调用没被预计数**（上限被拒后误起、编排例外轮不计次），不改计数，无产出时只记 `uncounted_calls`（`refunded: false`）。配到且没有产出就结束的调用把那一轮还回去，记进状态文件的 `uncounted_calls`（`kind`、`started_at`、`exit_code`、`reason`）；按 `kind` + `started_at` 去重，重复执行不多还。「没有产出」指：硬超时或无活动击杀（124）、模型容量错误（11）、或退出 10 且校验没跑（缺 `-o`、`turn.failed`、退出码非 0、被中止、留下进程）。拿到回答但校验不过（`validation: failed`）、位置断言失败（12）、孤儿（包装脚本没写完 `meta.json`）照计。
- `release <编号> test|impl|handover [--engine …] --reason <原因>` 或 `release <编号> review --review-type <类型> [--engine …] --reason <原因>`（CT-06zzzp，FU-CODEX-RUN-REJECT-COUNT）：**调用前就被拒绝时退回调用方已计的那一轮**。`codex-run.sh` / `claude-run.sh` 的拒绝（退出 2）都在写 `meta.json` 之前，`settle` 不会跑，所以由包装脚本在拒绝时调它。只退同 `kind`（`review` 按评审类型归 `spec-test` 或 `code`）、同 `engine`（默认 `codex`）、`bumped_at` 落在 `settle` 同一个配对窗口内（现在往前 `BUMP_MATCH_WINDOW_MS`，往后 `BUMP_CLOCK_SKEW_MS`）的**最新一条**未消耗待结算：标 `outcome: refused`，记 `reason`、`released_at`，对应计数减 1；更早的未消耗待结算不动。已被 `settle` / `opus-run` 消耗的（`kept`、`refunded`、`superseded`）不退，退过的（`refused`）也不会再被 `settle` 配对，所以同一轮最多退一次，重复调用无害。找不到可退的、或没有状态文件时什么都不写（不建文件），退出 0，输出 `nothing to release`。参数写法与 `bump-attempt` 相同，另必须带 `--reason`；参数错误退出 2、不改文件。可选 `--call <调用标识>`（CT-06zzzu，FU-CODEX-RUN-REJECT-COUNT-REST）：包装脚本每次调用生成一个标识，退掉的待结算记下 `call`；已有同 `kind`、同 `engine`、记着同一 `call` 的 `refused` 待结算时什么都不写，退出 0，输出 `nothing to release`，不再去退更早的那条，所以同一次被拒的调用重复 release 也只退一轮。`--call` 的值为空、只有空白或缺值时按参数错误退出 2；不带 `--call` 时行为照旧。不带 kind 的 `release <编号> [--owner …]` 仍是释放领用，两者互不影响（带 `--call` 也按参数错误退出 2）。退轮与其他写入者共用逐任务状态锁（CT-06zzzy，FU-STATE-RELEASE-LOCK，D10-947；见下文「逐任务状态锁」）：整段读-改-写（含 `--call` 的幂等判断）都在锁内做，没有状态文件、`nothing to release` 这些不写的路径也先拿锁再读；锁被占时照常等，等不到就退出 1、什么都不写；落盘在闸门内核对 `token`。输出格式不变。
- 不计轮次的调用照样计入每任务 10 次与连续无产出（见下一节）。
- `migrate <编号> [--unattributed-review spec-test|code] [--dry-run]`：把旧形状 `attempts: {impl, review}` 的状态文件换成新形状。评审轮次按 `<runs>/<编号>/` 下各次调用的 `meta.json`（`meta.<模式>.json` 与 `attempts/<n>/meta.json`）归到各自类型，没有产出的调用移进 `uncounted_calls`；实现次数减去没有产出的实现调用；其余字段（`state`、`last_error` …）不动。旧计数比留下的评审 `meta.json` 多时，必须用 `--unattributed-review` 说明多出的轮次归哪类，否则拒绝。旧形状的文件不经迁移读不进来（`get`、看板都会报错并提示这条命令）。

### 在途状态按台账收口（`state.ts reconcile`，CT-06zzzq）

FU-STATE-HYGIENE，编排 D10-900。台账是事实来源，`couli-runs/state/` 只是辅助：任务合并后状态文件常常没收尾，看板因此堆满告警。`node tools/ops/state.ts reconcile [--apply] [--done-only]` 不带编号，按台账把这些收掉；标准输出是一份 JSON 报告 `{apply, done_only, a, b, c, d, backup}`，四个列表按号排序。

- **台账从可信根读**（`COULI_TRUSTED_ROOT`，否则 `couli-runs/trusted/rebate-platform`，11 §2.4），用 `tools/lib/yaml-lite.ts` 的 `parseYamlLite` 解析 `ops/tasks/*.yaml`，只取顶层 `status`；归档（`ops/tasks/archive/<月>/*.yaml`）里的任务算 done。台账为空，或者有文件读不出、解析失败、`status` 不是 `todo` / `done` / `void`，就退出 1、什么都不写。不经 `tools/lib/task-file.ts` / `task.ts`（D10-948）：它们会连带加载 `tools/guard/**`，而 `state.ts` 的依赖要保持在 fsx、paths、cli、lock 加 yaml-lite（它不导入任何模块），因为测试夹具的可信根里只拷了 `tools/agent`、`tools/lib` 和几个 ops 文件；台账其余字段是否合法由 `task.ts check` 把关。状态文件经 `COULI_RUNS` 找，有一个读不进来同样退出 1。
- **四类口径**（一个号只进一类，按 A → B → C 的顺序判）：
  - A：台账 `done`，状态不是 `ready` → 置 `ready`，清 `pid`（连同 `started_at`），放租约（`owner_session`、`lease_until` 清空）。
  - B：记录的 `pid` 已不在（`kill -0`，EPERM 算活着）→ 只清 `pid`；台账未完成的任务状态、租约都不动（这条线回来时照 11 §2.5 按孤儿处理）。台账已 done 的任务（状态已是 `ready`）若租约也过期，一并放掉。`--done-only` 只收台账已 done 的 B，供夜间例行用。
  - C：台账 `done`，租约已过期 → 放租约。台账未完成任务的过期租约**不动**：那是某条线停了的真信号，看板按持有者列出，要人看。
  - D：有状态文件、台账里没有这个号 → 只列出，不碰（改号、作废还是误建由编排定，定了再手工删）。
  - `void` 不算 done：作废任务不进 A、C，只在 pid 已不在时按 B 清 pid（`--done-only` 时也不清）。
- **一律不动**：轮次（`attempts`）、`pending_bumps`、`uncounted_calls`、`opus_failures`、`opus_runs`、`spec_commit`、`implementer`、`last_error`，以及 `couli-runs/claims/<编号>/` 领用目录（`release` 会删领用目录，`reconcile` 不删；过期的领用别的会话照常接管）。只改上面列出的字段和 `updated_at`，其余字段与键序原样；不需要改的文件一个字节都不动。
- **默认 dry-run**：只出报告，不建目录、不写任何文件。`--done-only` 不带 `--apply` 时同样只预演。
- **`--apply`**：先用系统 `tar` 把整个 `couli-runs/state/` 打包成 `couli-runs/state-backups/<UTC 时间>.tgz`（如 `20261108T040000Z.tgz`，同一秒已有同名备份就拒绝）；打包失败就退出 1、不改任何状态文件。然后逐个写入：与其他写入者共用逐任务状态锁（见下一条），每个任务只试一次、不等，锁被别人占着就跳过（记进报告的 `skipped`，按号排序，下次再收）；拿到锁后在锁内重新读、重新分类，只写这时仍成立的修改。dry-run 不加锁，`skipped` 为空。接着往 `couli-runs/state-reconcile.log` 追加一行（时间、`a= b= c= d= skipped=` 各类条数、备份路径），最后删掉 `state-backups/` 里按文件名时间早于 7 天的 `.tgz`。再跑一次 `--apply` 只剩 D。
- **逐任务状态锁**（CT-06zzzq r1 S1、r2 S1）：`state.ts` 里每一处读-改-写状态文件（`set` / `claim` / `release` 走的 `updateState`、带 kind 的 `release`（退轮，CT-06zzzy）、`bump-attempt`、`settle`、`opus-run`、`migrate`、`reconcile`），都在 `couli-runs/state-locks/<编号>.lock` 下做。
  - **加锁**：普通的 `'wx'` 排他创建，内容 `{pid, acquired_at, token}`，`token` 每次加锁都新生成（`crypto.randomUUID`）。
  - **等待**：锁被占时最多等 `STATE_LOCK_WAIT_MS`（10 秒）。环境变量 `COULI_STATE_LOCK_WAIT_MS` 每次加锁时读，可以覆盖；`reconcile` 加锁时只试一次、不等，不受它影响（写入时等闸门照用这个上限）。等不到就退出 1，什么都不写。
  - **写入持闸门**：每次写状态文件（6 个写入入口和 `reconcile` 的每一条）都在持有接管闸门 `<编号>.lock.takeover` 时做：先重读锁核对 `token` 是自己的（不是就报错、不写），再落盘，最后放闸门。接管也要闸门，所以从核对到落盘之间锁不可能被别人接管，哪怕持有者在核对前暂停了很久。写入时等闸门的上限同样是 `STATE_LOCK_WAIT_MS` / `COULI_STATE_LOCK_WAIT_MS`，等不到就报错（消息含闸门路径），不写；`reconcile` 遇到这种情况把该任务记进 `skipped`，其余照收。
  - **删锁都过闸门**：所有删除 `<编号>.lock` 的动作也都在持有闸门（同样 `'wx'` 排他创建）时做，并且都是先重读、`token` 对上才删。没有人改名、覆盖或挪走别人的锁，所以持闸门期间锁文件不会被换掉，删掉的只会是核对过的那一把。
    - 释放：拿闸门（最多等 2 秒），`token` 是自己的才删，放闸门。
    - 陈旧接管：持有者 pid 已不在，或 `acquired_at` 早于 `STATE_LOCK_STALE_MS`（60 秒），算陈旧。接管者拿闸门（拿不到就回去照常等）→ 重读锁，`token` 仍是判为陈旧的那把才删 → 放闸门 → 再用普通 `'wx'` 抢锁。
  - **闸门卡住时人工处理**：闸门从不自动回收，即使留下它的进程已经死了。要加锁接管、写入或释放的进程等到上限后报错，消息里有闸门的完整路径，状态不写。先确认没有 `state.ts` 进程在跑（`pgrep -fl 'tools/ops/state.ts'`），再手工删掉那个 `.takeover` 文件；后面压着的陈旧锁由下一个写入者照常接管。
  - **位置**：锁和闸门都不放在 `state/` 里，所以 `state/` 只有 `<编号>.json`，备份包也不含锁。
- 不连库、不联网。`--apply`、`--done-only` 用在别的子命令上退出 2。

  - 槽目录：`COULI_VERIFY_SLOT_DIR`，默认 `couli-runs/verify-slot/`（即 `$COULI_RUNS/verify-slot`；不存在就建）。用 `COULI_RUNS` 分开的几条线要共用一个槽，须设同一个 `COULI_VERIFY_SLOT_DIR`。
  - 锁：槽目录下用 `mkdir` 原子创建的目录 `slot.lock`，里面的 `owner` 文件每行一个 `key=value`：`pid`（本脚本进程号）、`task`、`mode`（`verify:fast` / `verify`）、`started_at`（UTC）、`token`（每次运行唯一）。`owner` 先写临时文件 `owner.tmp.<pid>`，再用 `ln`（硬链接，不带 `-f`）放成 `owner`、删掉临时文件：读的人不会读到半个文件，已有 `owner` 时 `ln` 失败、不覆盖别人的（以前的 `mv` 会覆盖）。放好后读回 `owner`，`token` 是本次运行的才算拿到槽（CT-06zzzzy，D10-1365）；写临时文件失败、`ln` 失败或读回的不是自己的，就是没拿到：只删自己的临时文件，不删锁目录、不动别人的 `owner`，标准错误写 `lost the verify slot while taking it (now <持有者>): waiting again`，什么都不持有（释放时不动这把锁），回去照常排队，等待上限仍从最初开始算、等待报告照旧。
  - 起容器前核对（CT-06zzzzy，D10-1365）：取了槽的运行在起容器前再读一次 `slot.lock/owner`，`token` 仍是本次运行的才往下走。调用点：`--fast` 在起 verify 容器之前；默认完整验证在起服务（一次性 PostgreSQL / Redis 或宿主一次性服务）之前，以及起 verify 容器之前。不是自己的（换成了别人的、没有 `owner`、锁目录已不在）就在标准错误写 `the verify slot is no longer this run's (now <持有者>): not starting the services` 或 `… not starting the verify container`，退出 2：不起那个容器、不写 `result.json`、不动别人的锁（退出时的释放照旧核对 `token`，留给新持有者）。`--red`、`--related`、`--browser`、`--dry-run` 不取槽，也不做这项核对。
  - 等待：`COULI_VERIFY_SLOT_WAIT_SECS`（默认 1800，正整数）为上限；等待开始时与之后每 `COULI_VERIFY_SLOT_REPORT_SECS`（默认 60，正整数）秒在标准错误打印一行 `waiting for the verify slot held by task <编号> (pid …, 模式, since …): <已等>s of <上限>s`。两个变量取 0、负数、小数或非数字时退出 2（`… must be a positive integer`）。超过上限退出 2，最后一行写明 `gave up waiting for the verify slot` 与持有者（任务号、pid；因容器仍在跑而等的，还写明这一点），不起任何容器（为判陈旧最多调过 `docker ps`）、不写 `result.json`、不建运行目录，也不动别人的锁。完整验证（默认上限 3600 秒）排在另一次完整验证后面时可能等不到 1800 秒，必要时调大上限。
  - 持有者的 pid 还活着（含别的用户的进程：`kill -0` 失败但 `ps -p` 还在）就一直等，从不移走；`owner` 还没写出（只有目录）或读不出 pid 的锁也当作活的。pid 已不存在才可能陈旧：先用 `mkdir` 拿接管闸门 `slot.lock.takeover`，拿到后重读 `owner`，`token` 仍是判为陈旧的那一把，再查这把 token 的容器（下一条），确认没有在跑才删 `slot.lock`（标准错误写 `taking over the stale verify slot of task <旧编号> …`），然后删掉自己建的闸门，回去照常抢锁；闸门被活着的进程占着就照常等到上限（写一次 `stale verify slot of … the takeover gate … is held by …; waiting`），活着的人的闸门从不删。没有 `token` 的陈旧锁不接管。
  - 容器标签（CT-06zzzzb，#2751 S2-1）：取了槽的运行，跑 `verify:fast` 的那个 verify 容器（`--fast` 与 `pnpm verify` 各一个）多带一个标签 `couli.slot-token=<本次 token>`；一次性 PostgreSQL / Redis 与 fetch 容器不带（前两者不会自己结束，带了会让槽一直判为不陈旧）。持有者被 SIGKILL 时 trap 不跑，它的 verify 容器还在 Colima 里跑：判陈旧前（已拿到闸门、token 已核对）用 `docker ps -q --filter label=couli.slot-token=<陈旧锁的 token>` 查，有输出就不算陈旧、不删锁、放掉闸门照常等（写一次 `… is not stale: pid … no longer exists but its verify container (label couli.slot-token=…) is still running; waiting`）；`docker ps` 本身失败也一样按不陈旧处理（宁可等到上限也不并发）。这次 `docker ps` 是在闸门内跑的，所以有上限 `COULI_VERIFY_SLOT_PS_TIMEOUT_SECS`（默认 10 秒，正整数；取 0、负数、小数或非数字退出 2）：本机没有 `timeout`，由一小段 perl 把 `docker ps` 作为子进程放进它自己的进程组里跑，超过上限就把整组 SIGKILL 掉（docker CLI 是 Go 程序，会忽略 SIGALRM，所以不能只靠 alarm 再 exec），返回 124；脚本把它当作查询出错——不接管、放掉闸门、照常等，日志写 `… docker ps for its container (label couli.slot-token=…) timed out after <n>s …`。卡住的守护进程因此每次最多占闸门这么久，不会再挡住所有人；这个 perl 小助手被 INT / TERM / HUP 时也会先杀掉那组进程。同一个持有者最多每 5 秒再查一次，容器结束后的下一次检查查不到就照常接管。verify 容器自己受 `VERIFY_TIMEOUT_SECS` 限时，最晚到那时结束。
  - 孤儿锁（S2-2）：`slot.lock` 没有 `owner` 文件（`mkdir` 之后、写 `owner` 之前被中断），且目录本身的 mtime 早于 `COULI_VERIFY_SLOT_ORPHAN_SECS`（默认 30 秒，正整数；取 0、负数、小数或非数字退出 2）就算孤儿：拿闸门，在闸门内核对它仍没有 `owner`、仍是同一个目录（inode 与 mtime 都没变）才删（`removing the orphan verify slot …`）。时限内的无 owner 锁照旧当作活的、不动；闸门被活着的进程占着也不动。
  - 卡住的闸门（S2-2）：拿闸门失败时看现有闸门——`owner` 里的 pid 已不存在，或没有 `owner` 且目录 mtime 早于同一时限，就算陈旧。回收：先把闸门 `mv` 成本次独有的名字 `slot.lock.takeover.reap.<pid>.<随机数>`（改名是原子的，只会移走一个目录），再核对移走的正是判为陈旧的那个（inode、mtime、`owner` 全文都一致）才删（`removed the stale takeover gate … of task <编号> …` 或 `removed the orphan takeover gate …`），然后马上重新抢闸门；不一致（判定之后原闸门已被别人回收、又有人新建了闸门）就不删，闸门名空着时原样挪回去并写明。释放时拿闸门也走同样的回收。删自己的闸门前核对里面的 `token` 仍是自己的。
  - 残余窗口：① 回收闸门时如果移走的是别人刚建的新闸门，挪回去之前（几毫秒）又有第三个进程建了闸门，就会有两个进程同时以为持有闸门；只有它们又同时去接管同一把陈旧锁，才可能一个删掉另一个刚抢到的锁。这要求陈旧闸门、两个回收者和陈旧锁同时出现，概率极低；挪不回去时那个目录留在 `slot.lock.takeover.reap.*`，日志写明路径，可按下面的人工处理删掉。② 判孤儿看的是时限：一个活着的进程在 `mkdir` 与放好 `owner` 之间（或拿闸门与写闸门 `owner` 之间）停住超过时限（例如被 SIGSTOP、整机挂起），可能被当作孤儿删掉。它醒来时不再覆盖别人的 `owner`：别人已重建锁并放好 `owner` 时它的 `ln` 失败，读回不是自己的，写 `lost the verify slot while taking it` 回去排队（CT-06zzzzy）。若清孤儿的 `rm -rf` 恰在它放好 `owner`、读回之后才删掉目录，它以为拿到了槽，但在起容器前的核对处发现槽已不是自己的、退出 2，不会与新持有者同时跑容器（核对只在起容器之前做，容器起来之后锁才被删掉的情形仍在这一窗口里）。闸门的 `owner` 照旧写临时文件再改名。③ pid 被无关进程复用时陈旧锁或闸门一直显示为活，照旧要人工处理。④ 守护进程一直挂起时，每次检查都会等满 `COULI_VERIFY_SLOT_PS_TIMEOUT_SECS` 后判为出错，槽一直接不过来，等到上限退出 2（不会并发）；脚本本身被 SIGKILL 时 perl 小助手收不到信号，它的那次 `docker ps` 最多再跑到超时为止。

  - 释放：正常结束、失败、超时和被 INT / TERM / HUP 中断都经 EXIT trap 释放（在清掉本次容器之后）；释放也要先拿闸门（最多等 5 秒），核对 `token` 仍是自己的才删，锁已被换成别人的（`no longer this run's … left to its holder`）就不动。5 秒内拿不到闸门就把锁留下并写明，本进程结束后它按陈旧锁处理。退出码与 `result.json` 的语义都不变；`started_at` 是取到槽、导出快照之后的时刻，不含排队时间。
  - 人工处理（只在确认没有 verify-container 在跑时做，`ps -ef | grep verify-container.sh`；pid 已死或无 owner 超时的闸门与无 owner 的锁现在会自动回收，下面只剩自动处理不了的）：① 闸门的 pid 被无关进程复用而一直显示为活，等待一直报 `the takeover gate … is held by …`：`rm -rf couli-runs/verify-slot/slot.lock.takeover`；② 锁没有 `token`，或 pid 被无关进程复用而一直显示为活：核对 `slot.lock/owner` 里的任务确已不在跑之后 `rm -rf couli-runs/verify-slot/slot.lock`；③ 一直报 `still running`：用 `docker ps --filter label=couli.slot-token=<token>` 核对那个容器确属已被杀掉的运行后 `docker rm -f` 它，下一次检查就会接管；④ 留下的 `slot.lock.takeover.reap.*`：没有 verify-container 在跑时直接删。都只删这些目录，槽目录本身留着。
- 宿主一次性服务模式（负责人 2026-10-08 / 09：本机不跑 Docker，容器验证放到 AWS 测试机；测试库不进 Docker；10-09 定方案 A）。设 `COULI_VERIFY_HOST_SERVICES=1` 开启（其他取值退出 2），只改要连库的那次运行（`pnpm verify`、`--red` 里需要库的组），其余（`--fast`、`--browser`、只有单元组的 `--red`）与原来一样：

  | --- | --- | --- |
  | `COULI_VERIFY_SVC_USER` | `couli-svc` | 一次性服务的运行用户；只能属于下一行的组 |
  | `COULI_VERIFY_SVC_GROUP` | `couli-sock` | socket 的属组；只有本次的测试容器经 `--group-add` 拿到它 |

### 现在怎么手动走一轮（`tick.sh` 之前）

1. `pnpm ops:status` 看就绪任务与失败熔断。
2. 建 worktree `../couli-runs/worktrees/<编号>`（分支 `task/<编号>`）并在沙箱外 `pnpm install --frozen-lockfile`。
3. Codex 写规则测试（台账要先有 `test_paths`）：`tools/agent/dispatch.sh <编号>`（内部依次：`state.ts claim` → 核对台账 `test_paths` → `state.ts bump-attempt <编号> test`（含失败熔断） → `brief.ts --phase test` → 后台 `codex-run.sh impl --phase test`），结束后 `tools/agent/post-run.sh <编号>` 过守卫（`path-guard.ts --author`），输出 `red-check`：跑 `tools/ops/verify-container.sh <编号> --red`（隔离容器里只跑本任务新写的规则测试，`red-check.ts` 逐个文件对账），通过后提交 `test(spec): …`、`state.ts set <编号> --spec-commit <提交>`；RV2 再交 Claude 新子代理过审（`tools/agent/README.md` §11）。
4. Opus 实现：按 `tools/agent/README.md` §10 起 Claude 子代理（`bump-attempt <编号> impl` → `brief.ts --phase impl` → 子代理 → 位置断言 → 守卫 → `state.ts opus-run --run-id …`）。
5. 完整验证看 PR 头提交上的必过检查（GitHub CI：ci-gate、contracts-gate、longrun-props；`ops/approvals.yaml` 第 21 条，2026-10-06 起）；`tools/ops/verify-container.sh <编号>` 仍可在本机跑，结果可选地写进证据文件（写了就必须在头提交树上通过）。
6. 失败要重派时：先 `node tools/ops/state.ts set <编号> --last-error <verify/<n>/log.txt 的路径>`，然后回到第 4 步（Opus 超限后 RV0 / RV1 换家：`dispatch.sh <编号> --handover`）。`dispatch.sh` 先计数再生成任务书，从第 2 次尝试起每次都重新生成，所以新任务书会写「第 n 次尝试」并带上一轮失败输出的末尾。`last_error` 目前没有脚本自动写，漏了这一步新任务书就没有失败输出。
